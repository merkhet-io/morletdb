Open source · alpha · PostgreSQL extension

Recordings,
not rows.

MorletDB keeps high-rate sensor recordings (vibration, current, acoustic, seismic) inside PostgreSQL. It stores every sample losslessly, finds similar intervals across the archive, and gives AI agents read-only tools to investigate them, from a Raspberry Pi at the machine to a server.

Primary use case / AI

Give agents signal evidence to reason with.

An investigation agent can search your recording archive before it answers: “Have we seen a signal like this before?” MorletDB supplies matching intervals and their original samples. Your application connects them to analysis tools, maintenance notes or experiment records.

EXAMPLE / FACTORY INVESTIGATION AGENT
“This cycle looks unusual. Have we seen this signal before? Compare earlier runs and bring back the evidence for review.”
01 / RETRIEVESearch the relevant history.

The agent calls a bounded SQL tool with a source interval, asset filter and result limit.

02 / INSPECTBring samples into analysis.

Read matching intervals and pass them to a plotting, signal-processing or model tool.

03 / EXPLAINLink the answer to its evidence.

Return recording IDs and sample ranges alongside comparisons so an engineer can inspect the source.

Integration pattern using existing SQL primitives. Detection models, agent orchestration and machine controls are supplied by your application. Agent and anomaly-detection effectiveness have not been evaluated; similarity alone does not establish normality, a fault or its cause.

Built around signals

From a similar shape to the original evidence.

Lossless recording storage

Compressed raw chunks preserve the samples you ingest. Read intervals back across chunk boundaries.

Search with room for a time shift

Bounded-lag envelope search compares signal structure without requiring exact zero-lag alignment.

Keep context in the query

Use JSONB metadata filters to narrow your archive by asset, experiment or operating condition.

Choose exact or indexed retrieval

Use an exact scorer or optional pgvector probes with exact re-ranking. Indexed candidate selection trades recall for latency.

Newest data in one call

morlet_latest returns every matching sensor’s last samples or newest chunk statistics, at a fixed number of index lookups per recording.

React to new data

Commit notifications send one pg_notify per committed transaction with the stored sample ranges; rolled-back and replayed writes send nothing.

Channels sampled together

Declare a synchronous group: its channels are appended in one transaction, read by sample index, and summarized exactly across channels, such as real power.

Statistics over years

Exact roll-ups merge chunk summaries, so min, max, mean and RMS over long intervals come from a few rows, bit for bit the same as decoding every sample.

The workflow

Append. Search. Read.

Store a recording, find similar intervals, and inspect the original samples. The same SQL connection carries you from measurement to result.

-- Append at the recording’s next sample offset.
SELECT morlet_append_chunk(
  'public.getting_started', 'run-a', 0,
  ARRAY(SELECT sin(i::float8 / 8)
        FROM generate_series(0, 8191) AS i ORDER BY i)
);
-- Search a stored interval with a metadata filter.
SELECT * FROM morlet_search_envelope_interval(
  'public.getting_started', 'run-a', 0, 4096,
  '{"asset":"spindle-1"}'::jsonb, 10
);
-- Read original samples from an interval.
SELECT * FROM morlet_read_interval(
  'public.getting_started', 'run-b', 0, 4096
);

Illustrative SQL calls, not a live database. Create the collection and recordings before appending, then explicitly build envelopes before searching. The guide contains the complete runnable sequence.

Get started

Bring your recordings to PostgreSQL.

Run the prebuilt release image (PostgreSQL 17 with pg_morlet, no compiling), try the Docker walkthrough with synthetic data, or build the extension with Rust and pgrx. PostgreSQL 17, 18 and 19 are supported by the compatibility matrix. Release images and paper benchmarks use 17. For an existing PostgreSQL 17 or 18 server on Debian, install the release’s package (amd64, arm64; installed with apt and tried before each release). PostgreSQL 19 (release candidate 19rc1) builds from source; images and packages for 19 follow 19.0. PostgreSQL 19 compresses large values with lz4 by default; MorletDB pins its sample and envelope columns to pglz, so storage is byte for byte the same as on 17 and 18 (compatibility).

docker run -d --name morletdb -e POSTGRES_USER=morlet -e POSTGRES_PASSWORD=change-me \
  -e POSTGRES_DB=morlet -p 127.0.0.1:54329:5432 -v morletdb-data:/var/lib/postgresql/data \
  ghcr.io/merkhet-io/morletdb:0.3.9-alpha.1
docker exec morletdb psql -U morlet -d morlet -c "CREATE EXTENSION pg_morlet"

The release image is Linux amd64 and arm64 and does not include pgvector (needed only for indexed probe search). Or try the walkthrough with synthetic data:

git clone https://github.com/merkhet-io/morletdb.git
cd morletdb
docker compose run --rm walkthrough

Requires Git and Docker Compose v2. The first run builds the extension and uses synthetic recordings. pgvector is optional for indexed probe search and is not included in this walkthrough. Developer alpha.

When to use it

When your application needs to investigate signals.

Use MorletDB when you have uniformly sampled recordings (single channels, channels at different rates grouped into acquisitions, or synchronous groups sampled at the same instants), want to find similar intervals, and need to inspect the original evidence in its context.

PRIMARY / AGENTIC INVESTIGATIONRetrieve signal history before answering.

Connect an AI agent through the bundled read-only MCP server, or give it your own SQL tool, to search similar intervals, inspect their samples, and link its analysis to recordings. Combine results with your own maintenance or experiment records.

ANOMALY WORKFLOWSPut an unusual signal in context.

Use historical retrieval alongside an external anomaly detector to review flagged intervals and collect comparison examples. Detection thresholds and fault labels belong to your application.

AUTOMATED TRIAGEGive automated decisions a signal history.

Support agents that gather evidence across machine runs before proposing maintenance, requesting a quality check or escalating an unfamiliar event. Operational benefits remain to be validated.

CONDITION MONITORINGRevisit a suspicious machine cycle.

Compare vibration or motor-current intervals with earlier runs, filtered by asset, operating mode or experiment. A target application; fault diagnosis is not validated.

TEST & MEASUREMENTFind a familiar transient in your test archive.

Keep sensor recordings beside test metadata. Retrieve a matching interval and read its original samples for engineering review.

SEISMIC RESEARCHFind event-shaped signals despite small time shifts.

Search seismic envelopes with bounded-lag correlation. This is the domain used in the published retrieval experiments.

ACOUSTIC INVESTIGATIONCompare recurring sounds and bursts.

Explore similarity in uniformly sampled acoustic recordings from equipment or experiments. A candidate workflow, not evaluated speech or audio understanding.

A good fit if…

Your application already uses PostgreSQL, needs metadata filters, and must connect search results to exact source intervals. Search requires compatible sample rates, channels, units and representation settings.

Use cases beyond the evaluated seismic and appliance-current retrieval (N1) are proposed applications. MorletDB does not provide automatic diagnosis, speech recognition, resampling or multichannel similarity search.

Theory

How MorletDB looks at a signal.

A fault rarely shows in one reading. It shows as a shape over time, a knock that rings out, and as energy in one frequency band at that moment. In the picture, both similar events rise as peaks in the same band.

  1. Recording. Samples on a fixed clock: start and rate are stored once, each time follows exactly.tn = t0 + n / fs
  2. Envelope. The signal’s loudness over time, the magnitude of its analytic signal. Similar events share it even when their oscillations don’t line up.e(t) = |x(t) + i·ℋ{x}(t)|
  3. Search. Compare envelopes, allowing a small time shift τ, and return the original samples of the best matches.d(q, w) = 1 − max|τ| ≤ L corr(eq, ew(· + τ))

Questions like have we seen this before? are about intervals of a signal; this is the primitive that answers them.

Recordings, not rows

What you don’t have to build.

A general time-series database stores rows of timestamped values. MorletDB stores recordings, so the work around waveforms that you would otherwise build yourself is part of the database.

TaskGeneral time-series databaseMorletDB
Data modelA row per sample: timestamp, tags, values. You design tables per sampling rate, tag columns and partitions, and every row carries its own time.A recording: rate, start, channel, unit and metadata, stored once. Samples are addressed by index or by time, and each sample’s time is derived exactly. In B3, time and identity were a third of QuestDB’s native row size.
Channels at different ratesA table per rate, or sparse wide tables. Aligning a moment across them takes a range query per table and timestamp arithmetic in the client.An acquisition groups channels with their own rates, clock offsets and clock uncertainty. One call reads a time interval from every channel, each in its own samples.
Resending dataDeduplication often keeps the last write: in B3, an altered resend silently replaced QuestDB’s stored values.An identical resend changes nothing; an altered resend is refused and the stored samples stay as they were.
Operating conditionsTags repeated on every row, or a separate table joined by time.Context intervals (program, tool, load, part) become segments with comparable values. A segment is compared with the same unit’s history under the same conditions, optionally only with what came before it.

Typed tools only, no arbitrary SQL, every call in a read-only transaction under your database role.

Landscape

Where MorletDB fits.

Most time-series systems are built for rows of readings: metrics, events and analytics. MorletDB is built for the high-rate recordings behind them, and it runs inside PostgreSQL. The quadrant shows what each system is designed for and where it runs, from its own documentation; it is not a ranking. “Inside PostgreSQL” means running in a PostgreSQL server; CrateDB accepts PostgreSQL clients through PostgreSQL’s wire protocol but is a separate database server.

At the edge

Built to run at the edge.

Waveforms are recorded next to the machine, and that is where MorletDB can keep them: on an industrial PC, an edge gateway or a NUC beside the line. It is a PostgreSQL extension with a small footprint, stores every sample exactly, and keeps search, statistics and context on the device, so an engineer or an agent can investigate locally without shipping raw data to the cloud first. To buffer data at the machine, Akhet, a separate collector from the same maintainers, commits MQTT messages and Modbus TCP registers to a local spool before acknowledging them and replays them into MorletDB later; process crashes are tested, power loss not yet. Container images are published for x86-64 and arm64.

TESTED ON A RASPBERRY PI 3B+ · X2

To test the low end, we ran it on one of the smallest common single-board computers. In all nine runs, the same image ran the full workflow on a Raspberry Pi 3B+ (4 × Cortex-A53 at 1.4 GHz, 1 GB RAM, microSD card, no fan), within the same 2 CPUs and 512 MB, with the client on the device: durable ingestion with search features, exact reads, statistics and similarity search. Every sample came back bit for bit, and similarity search returned exactly the same results as on the desktop.

Medians of three fanless runs per arm (1.2 GHz at the soft temperature limit): 78,000 samples/s durable ingestion with search features, and 258,000 samples/s as plain lossless storage. That keeps up with about three vibration channels at 25.6 kHz searchable, or about ten stored. Reads of 4,096 samples took 6.4 ms (p50) and a top-10 similarity search 0.6 s; the container peaked at about 120 MiB of its 512 MB (Docker’s measure).

One device, one dataset; not tested for long-term operation or power loss. X2 results ↗

Exact search with long windows is cache-aware since 0.3.8-alpha.1: on the Pi, a query over 1,341 windows of 16,384 samples takes 1.5 s instead of 15.1 s, with bit-identical results; desktops are unchanged (edge latency ↗).

SELF-MAINTAINING · STEWARD · 0.3.8-alpha.1

Next to a machine there is no database administrator. tools/steward runs the rebuildable upkeep (envelopes, summaries, roll-ups, verification, statistics) in one budgeted loop, only when the machine is not busy, records every action and shows one plain status. At the disk reserve it holds ingest: appends fail with a clear reason (SQLSTATE 53100) before PostgreSQL runs out of space, and resume when space is free. Its role cannot remove stored samples; changes to stored samples and extension updates are plans that a second person approves.

Tested by filling a real disk on a Raspberry Pi 3B+: new recordings were refused at 295 MB free (300 MB reserve), with no PostgreSQL write error; 14.5 s after space was freed, recording resumed on its own, and every acknowledged sample read back bit for bit.

Not yet tested: power loss and weeks of operation. Disk-fill results ↗ Blog: self-driving Postgres on the edge

Engineering you can check

Claims you can rerun.

A database earns trust with evidence, not adjectives. Everything below is in the repository, so you can check it yourself instead of taking our word for it.

Protocols frozen before measuring

Every study commits its protocol and acceptance criteria before the confirmation run, tunes only on a separate development set, and appends every deviation. Losses are reported next to wins, and raw results are in the repository.

Every sample read back

Every load in the B3 benchmark and the X1 and X2 small-machine studies ends by reading every channel back and comparing it bit for bit with the source: 868 channels and 101.6 million samples, each time.

The codec is machine-checked

Kani proofs on the chunk codec, nightly fuzzing of decoding and round trips, and frozen golden chunk files that a change may not alter, so stored data stays readable (verification).

Upgrades and releases are tried

An upgraded catalog must equal a fresh installation, including the upgrade from the released version. Release images for x86-64 and arm64 run the quickstart from a clean checkout, and again after a restart, before they are published.

PostgreSQL underneath

Durable commits, transactions, backups, roles and row-level security come from PostgreSQL itself. An altered resend of stored samples is refused rather than overwriting them.

Agents stay read-only

The MCP server exposes typed signal tools only, with no arbitrary-SQL tool; each call runs in a read-only transaction with a statement timeout, as your database role (MCP). Every search result states what was searched and what was not, so a “no match” says what it covered.

Scrubbed on demand

morlet_verify re-reads every chunk (structure, CRC-32C, summaries, gaps) and reports problems without changing data; the steward runs it every week.

MorletDB is alpha software: there is no supported production release or security SLA yet (security policy). Long-term operation and power loss are not yet tested.

Direction

An archive that lasts, and remembers.

The vision at the top of this page, in more detail: what has shipped toward it, and what comes next.

A recording archive is not a log that only grows. Over years it has to stay fast to search, affordable to keep, and able to answer the question engineers actually ask at the machine: have we seen this before, and what was it? Two lines of thought guide the design.

SCALING: GROW BY YEARS WITHOUT SLOWING DOWN
Slices, not one big tableStorage and indexes should be cut by time, so that a search, an index rebuild or a retention step touches only the period it concerns, and a time and metadata filter decides which slices a search visits at all.
Exact summaries at every scaleShipped: per-chunk summaries and exact roll-ups over blocks of chunks keep statistics over a year in milliseconds, bit for bit. Next: they should be what remains when raw samples move on.
Tiers that keep their proofOld recordings belong on cheaper storage as checksummed files, with their metadata, context and summaries still in the database, so they can be found, judged and restored without guesswork.
EPISODIC MEMORY: REMEMBER LIKE AN ENGINEER
Episodes, with their outcomeAn incident, an operation or a confirmed investigation is an episode: an exact interval, its operating context and what it turned out to be. Shipped: episodes with context and importance. Next: recall that returns all three, so the next investigation starts where the last one ended.
Similarity, recency, importanceCloseness of shape alone is not memory. Recall should weigh how similar, how recent and how important an episode is, and a library of known incidents should stay searchable however old it is.
Forgetting on purposeA memory that only accumulates drowns in repetition. Shipped: four graded levels (not searchable, represented by another episode, summarized, gone), each move in one transaction with a ledger row; study F1 measured what forgetting costs recall and recommends recency as the default. Next: policies that propose the moves, approved by a person.

The argument is set out in report 2, Machines with a Memory (draft) ↗; F1 results in forgetting_f1 ↗.

Status

An open research project.

Built for investigating signal archives. Condition monitoring motivated the work. The report’s retrieval evaluation is seismic; study N1 added appliance identification from current transients, where search matched a current-feature baseline but did not flag unknown appliances. MorletDB is named in honor of Jean Morlet and the project’s initial wavelet hypothesis. Its representations are replaceable, and the current envelope search does not depend on a Morlet transform.
