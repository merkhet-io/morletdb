A database nobody has to look after

Next to a machine tool there is no database administrator. There is an operator who sees a screen, and somewhere a controls engineer who needs a ticket to restart the box. A database that only stays healthy if someone opens a shell will, in practice, not stay healthy. Builders fall behind, the disk fills, and the first sign is a search that quietly finds less than it should.

So we want MorletDB to look after itself. The idea is old: databases that tune and repair themselves have been a research goal for years, and the cloud has shipped parts of it. What has lasted in production is not the clever part. It is the boring part: act only within hard limits, check the result, undo it when it did not help, write everything down, and switch yourself off when things keep going wrong. That is what we want to copy, and it suits MorletDB unusually well.

Why MorletDB is a good candidate

  • Its upkeep is already explicit. Building search envelopes, chunk summaries and roll-ups, and verifying stored data, are SQL calls that do a bounded batch and return how much is left. A supervisor only needs to call them until they say 0. A killed job resumes without duplicates.
  • What can be rebuilt is separate from what cannot. Raw samples are the only thing that cannot be recomputed. Everything that makes them fast to search is derived. Under pressure the system can give up speed before it gives up data.
  • Forgetting is already a recorded act. Removing data goes through memory levels with a dry run and a ledger entry with the bytes freed and a checksum of what was removed, never through a silent age-based delete.
  • It can prove it is consistent. Chunks carry checksums and summaries are checked against them, so a health check is a proof, not a guess.
  • It is PostgreSQL underneath. Crash recovery, transactions, roles and backups are inherited rather than reinvented.

The line it must not cross

Most self-tuning systems risk a slow query that gets rolled back. MorletDB stores recordings that cannot be measured again. So the rule is narrow on purpose: automate every job whose output can be rebuilt, ration the disk on its own, and never delete raw data unless a person approved that exact plan and a verified copy exists elsewhere. It will also never update itself; in a plant, updates go through change control.

When the disk runs short, the order is fixed. Warn early, in time remaining rather than percent. Pause background work. Drop rebuildable search data if a policy allows it. Then refuse new recordings, with a clear reason. Refusing new data is a visible failure someone can fix. Losing old data unnoticed is not.

What the operator sees

One state: Normal, Attention or Action required, as industrial screens already do it. Each item says what is happening, what happens if nobody acts, one action and who should take it: “Disk full in about 6 days at the current recording rate; then new recordings are refused. Maintenance: add storage or confirm export.” Things the system fixes by itself are logged, not alarmed. The same status is available to the plant’s screens, to monitoring and, read-only, to AI agents over MCP.

Where this stands

This is a design, not a feature. Nothing schedules the jobs yet, there is no disk signal, and MorletDB has not yet passed a power-cut test or a long soak. The plan, the guardrails and the test that will say whether it works are in issue #287 ↗, with the metrics in #197 ↗ and the soak in #191 ↗. Comments and objections are welcome there.
